## Next.js 는 어떤 기술일까?

- React.js 를 보다 강력하고 편하게 사용할 수 있는 기능들을 제공한다.

### Next.js는 라이브러리가 아닌 프래임워크 이다.

- React.js 전용의 웹 개발 프레임워크

#### 기능 구현의 주도권이 누구에게 있는가?

- 주도권이 개발자에게 없다. 이를 Framework 라고 부른다.
- Framework가 제공하는 기능을 이용하거나 허용하는 범위 내에서만 추가 도구를 사용 가능하다.

> Q. 자유도가 높으면 좋은 것이 아닐까?

- 자유도가 너무 높아도 문제가 될 수 있다.
  - 기본 기능 외 제공되는 것이 없기 때문에 일일이 라이브러리를 추가하거나, 기능을 개발해야 한다.

### 사전 렌더링 이해하기

- 브라우저의 요청에 사전에 렌더링이 완료된 HTML을 응답하는 렌더링 방식이다.
- 렌더링 단계
  - 사용자의 요청
  - 서버에서 JS 실행 및 렌더링
  - 렌더링된 HTML 을 브라우저에 전달
  - HTML을 화면에 렌더링 (단, 인터렉션 불가)
  - 후속 작업으로 JS bundle 전달 -> 클라이언트(브라우저)에서 JS 실행 (html과 연결)
    - 이 단계를 수화(hydration)이라고 부른다.
  - TTI (Time To Interactive): 웹 페이지가 완전히 상호작용이 가능(interactive)하게 되는 시점.
    - 즉, 사용자의 접속 요청부터 수화 까지 걸리는 시간.
- 그렇다면, 사용자의 페이지 이동 요청은 어떻게 동작할까?
  - CSR(Client Side Rendering)과 동일하게 동작한다. (즉, 기존 React.js 와 동일)
  - 수화를 위한 단계에서 JS bundle 이 전달되기 때문이다.

즉, `기존 React App 의 단점을 해소하여 빠른 FCP 달성`하고, `React App 의 장점인 빠른 페이지 이동`을 할 수 있다는 장점이 있다.

#### CSR (Client Side Rendering)

- 클라이언트(브라우저)에서 직접 화면을 렌더링하는 방식이다.
- 렌더링 단계

  - 사용자의 요청
  - 서버에서 index.html (빈 껍데기) 전달.
  - 브라우저에서 빈 화면 렌더링
  - 후속 작업으로 JS bundle (이 서비스에서 접근 가능한 모든 컴포넌트 코드 존재) 전달 -> 클라이언트(브라우저)에서 JS 실행

- CSR 의 장단점.
  - 장점: 페이지 이동이 매우 빠름. (즉, 초기 접속 이후에 새로운 페이지를 요청할 필요가 없음)
  - 단점: 초기 접속 속도(FCP, first contentful paint)가 느림. (`요청 시작 ~ 컨텐츠 렌더링` 에서 걸리는 시간)
